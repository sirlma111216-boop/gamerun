# Claude Code 전달 지시서: 강의 앱에 루미 런 발표자 선정 활동 연결

아래 내용을 현재 강의 앱을 개발하는 Claude Code에 전달하세요. 실제 Render 게임 주소는 기존 배포 설정에서 찾거나 사용자가 제공한 주소로 채워야 합니다. 게임 저장소는 `https://github.com/sirlma111216-boop/gamerun.git`입니다.

---

## 요청

현재 개발 중인 강의 앱에 이미 독립 배포된 횡스크롤 멀티플레이 게임 **루미 런**을 활동 모듈로 연결해 주세요. 설명이나 목업에 그치지 말고 기존 앱의 로그인·수업·참가자·발표자 기능을 조사한 뒤 실제 연결과 검증까지 진행해 주세요. 작업 설명은 쉬운 한국어로 해 주세요.

### 원하는 사용자 흐름

1. 강사가 수업에서 ‘게임으로 발표자 선정’을 엽니다.
2. 강사 계정에는 **교사 방 만들기와 교사용 운영 화면만** 보입니다. 학생 참가 탭이나 자기 자신을 학생으로 등록하는 화면은 보이지 않습니다. 강사는 관전하며 참가 인원과 선정 인원을 관리합니다.
3. 학생 계정에는 **학생 참가 화면과 자기 게임 화면만** 보입니다. 방 만들기, 교사 전환, 규칙 변경, 강제 종료, 재경기 권한은 없습니다.
4. 앱에 로그인한 학생 ID·기존 닉네임을 그대로 사용합니다. 닉네임과 코드를 다시 입력하게 하지 않습니다. 닉네임은 캐릭터 위와 결과에 동일하게 표시합니다.
5. 방이 없으면 학생에게 ‘선생님이 게임을 준비하고 있어요’를 보여 줍니다. 강사가 방을 만들면 현재 활동을 연 학생의 브라우저가 같은 방에 자동 참가합니다. 활동을 아직 열지 않은 학생은 참가 대기로 표시합니다.
6. 강사는 현재 수업의 참가 대상 명단과 게임에 실제로 연결된 학생 수를 확인하고, 발표자로 선정할 인원 N을 지정합니다.
7. 경기가 끝나면 선정된 학생을 강의 앱의 **발표자**로 표시하고 기존 발표자 목록·다음 활동과 연결합니다. 결과는 새로고침해도 유지되어야 합니다.
8. 강사 선두 관전, 학생 자기 캐릭터 화면, 모바일 가로 안내와 터치 조작은 유지합니다.

## 먼저 조사할 것

- 강의 앱의 프레임워크, 폴더 구조, AGENTS.md, 실행·검사 명령, 기존 UI 컴포넌트.
- 로그인 세션과 실제 강사/학생 역할을 서버에서 판단하는 위치. 이메일이나 화면 선택으로 역할을 새로 추정하지 않습니다.
- 수업 ID, 활동 ID, 수업 참여자 ID·닉네임, 출석/접속 정보, 기존 실시간 통신 방식.
- 기존 발표자 저장 형식, 학생 카드·발표 순서·수업 실시간 알림 기능.
- 환경변수에 실제 Render 주소가 있는지. 없으면 이 주소만 사용자에게 요청하고 다른 조사·구현은 계속합니다. 예시 주소로 동작 확인을 했다고 보고하지 않습니다.
- 게임 저장소의 최신 코드를 읽고 아래의 확인 사항과 달라졌는지 확인합니다. 이 지시서는 게임 커밋 `73840ff` 기준으로 작성되었습니다.

기존 앱의 인증·DB·실시간 연결을 재사용하세요. 새 계정 시스템이나 다른 호스팅으로 이전하는 일을 추가하지 마세요. 접근 가능한 로컬 게임 저장소가 없다면 위 GitHub 소스를 별도 작업 폴더에 가져와 수정 범위를 관리하세요.

## 현재 게임이 실제로 지원하는 기능과 부족한 기능

현재 구현을 확인한 파일:

- `src/game/module.ts`: `LumiConfig`, `LumiAPI`, 화면 생성, 방 생성·참가 처리.
- `src/embed.ts`: iframe 메시지 연결.
- `src/game/network.ts`: 소켓 연결·참가 자격·재접속.
- `server/index.ts`, `server/room.ts`: 서버 방·권한·경기 상태.
- `shared/types.ts`, `shared/results.ts`: 규칙·결과 형식·선정 계산.
- `docs/INTEGRATION.md`, `docs/RULES.md`, `docs/DEPLOYMENT.md`: 기존 연결·규칙·배포 설명.

| 기능 | 현재 상태 |
|---|---|
| `participant: {id, name}` | 지원. 학생 ID와 닉네임 전달, 이름 입력 고정 |
| `activityId`, `storageKey`, `map`, `rules` | 지원 |
| `serverUrl`, `joinBaseUrl` | 지원 |
| `onReady`, `onStart`, `onEnd`, `onResult` | 지원 |
| `start`, `stop`, `restart`, `destroy`, `practice`, `getState` | 공개 API로 지원 |
| 강사/학생 화면을 고정하는 config 옵션 | **미지원. 추가 구현 필요** |
| 공개 `createRoom()` / `joinRoom()` API | **미지원. 추가가 필요할 때 구현** |
| 명단 전달로 자동 참가 | **미지원. 각 학생 브라우저의 실제 접속 구현 필요** |
| 강의 앱 계정으로 방 접근 권한 검증 | **미지원. 서버 연동 필요** |
| 발표자 결과의 강의 앱 DB 저장 | **미지원. 강의 앱에서 연결 필요** |

`participant`를 지정해도 현재 교사/학생 탭을 제한하지 않습니다. 존재하지 않는 config를 전달해 놓고 구현이 끝났다고 하지 마세요. CSS나 Shadow DOM 내부를 외부에서 강제로 조작하는 임시 방식 대신 게임의 공개 설정과 서버 규약을 확장하세요.

현재 `src/embed.ts`는 `lumi:available`에 버전 `1.0.0`을 하드코딩하고 있습니다. 실제 게임 버전 상수와 일치시키고 새 연동 기능의 지원 여부도 별도 capabilities로 알리도록 수정하세요.

## 권장 연결 구조

기본은 **강의 앱 안의 iframe + Render의 게임 화면·서버**입니다. 부모 앱의 프레임워크와 게임 Canvas를 분리하고 한 곳에서 게임 버전을 관리합니다.

역할:

- 강의 앱 서버: 사용자 인증, 수업 소속, 참여 대상, 활동 방 연결, 발표자 결과 저장.
- Render 게임 서버: 방 생성·참가 권한 확인, 움직임·충돌·순위·선정의 최종 계산.
- 강의 앱 화면: 역할에 맞는 진입, 활동 상태 공유, 발표자 표시.
- 게임 iframe: 닉네임을 전달받아 자신의 소켓으로 참가하고 게임을 표시.

이미 앱이 ES 모듈 방식으로 연결되어 있다면 그 구조를 활용해도 됩니다. 그 경우 `dist/module/lumi-run.js`를 앱과 같은 출처의 경로에 두고 `serverUrl`을 Render WSS 주소로 지정하세요. 현재 Render 서버에 다른 출처의 JS import를 허용하는 HTTP CORS가 있다고 가정하지 마세요. WebSocket의 `ALLOWED_ORIGINS`는 HTTP CORS와 별개입니다.

## 추가 구현 계약 — 아래 이름은 제안이며 현재 API가 아님

게임의 단독 실행을 유지하면서 연동 화면에 다음 기능을 추가하세요. 공개 이름을 바꾸면 사용처와 문서를 함께 맞춥니다.

```ts
// 새로 구현할 설정 예시. 기존 LumiConfig에 이미 있는 옵션으로 오해하지 말 것.
type LessonEntryConfig = {
  entryRole: 'teacher' | 'student'; // 화면 제어용. 서버 권한 증명이 아님
  roomCode?: string;
  autoJoin?: boolean;
  integrationTicket: string;       // 서버 검증용, 짧은 유효기간의 수업·활동·사용자 한정 증명
};
```

- `entryRole`이 생략되면 독립 게임의 기존 진입 화면을 유지합니다.
- teacher: 교사 진입 화면만 제공하고 사용자 클릭으로 방을 만듭니다. 페이지 렌더링마다 방을 자동 생성하지 않습니다. 기존 진행 방이 있으면 재접속합니다.
- student: 학생 진입만 제공하고, 방 코드·인증된 사용자 정보가 준비되면 한 번만 자동 참가합니다. 다시 로그인하거나 다른 활동으로 이동할 때 이전 계정의 참가 자격을 사용하지 않습니다.
- 첫 화면, 처음으로, 결과 후 돌아가기, 새로고침·재접속의 모든 경로에서 역할 제한을 유지합니다. 연동 화면의 혼자 연습·샘플 강의 링크 등 불필요한 독립 진입도 노출하지 않습니다.
- 초기 방 생성·참가 로직을 내부 공통 함수로 분리하고, 부모가 직접 제어해야 하는 경우에만 `createRoom`·`joinRoom` 및 iframe 명령을 공개하세요. 버튼 클릭과 API가 서로 다른 로직을 갖지 않게 합니다.
- `storageKey`는 최소 수업·활동 실행 ID·계정·역할을 포함해 분리합니다. 같은 수업에서 활동을 두 번 실행한 경우도 구분합니다.

### 서버 권한

화면에서 교사 버튼을 숨기는 것만으로 권한 처리가 끝난 것은 아닙니다. 현재 단독 서버는 누구나 일반 방을 만들 수 있고, 클라이언트가 학생 ID·이름을 전송합니다. 연동 방은 별도로 구분하고 아래 검증을 추가하세요.

1. 강의 앱 서버가 현재 로그인 세션의 역할·수업 소속·참여 자격을 검증합니다.
2. 검증된 사용자에게 해당 활동에 한정된 짧은 유효기간의 서명된 참가/교사 증명을 발급합니다. 기존 신뢰할 수 있는 인증 연동 방식이 있으면 재사용합니다.
3. 게임 서버가 서명·발급자·대상·만료·수업/활동·역할을 확인한 뒤 방을 생성하거나 참가시킵니다. ID와 닉네임은 검증한 정보에서 가져오고 브라우저가 임의로 보낸 값을 신뢰하지 않습니다.
4. 티켓의 활동과 실제 방의 활동을 대조합니다. 다른 수업의 코드만 알아도 들어갈 수 있게 하지 않습니다. 단독 방 생성으로 연동 활동 ID를 사칭하거나 결과 저장 대상으로 사용할 수 없어야 합니다.
5. 교사 설정·종료·재경기는 서버에서 교사만 허용합니다. 재접속 시도 역시 사용자·역할·방이 일치해야 하며 만료 티켓 갱신 흐름을 제공합니다.
6. 서명 키와 서버간 비밀은 서버 환경변수에만 보관합니다. 수업 전체 명단, 교사 토큰, 로그인 세션을 URL 쿼리나 전체 학생 방송에 넣지 않습니다. 개인 티켓은 HTTPS 응답 후 정확한 대상 iframe에 전달하고 소켓의 최초 인증 메시지에 사용합니다.

일반 단독 방의 기존 동작을 전부 없앨 필요는 없습니다. 연동 방만 인증된 수업 컨텍스트와 연결하고, 일반 방의 결과가 강의 앱 발표자를 바꾸지 못하게 하세요.

## 참가자 명단·인원·방 공유

- `roster`는 기존 수업의 참여 대상 학생 목록이며 ID·닉네임·참가 대상 여부를 재사용합니다. 강사 계정은 선수 인원에 포함하지 않습니다.
- ‘대상 학생 25명 / 게임 연결 22명 / 미참가 3명’처럼 서로 구분합니다. 출석, 강의 앱 접속, 게임 소켓 접속은 동일한 상태가 아닙니다.
- 학생 25명 명단을 넘겼다는 이유로 교사 브라우저가 25개 소켓이나 가짜 플레이어를 만들지 않습니다. 각 학생 기기에서 자신의 계정으로 접속해야 조작할 수 있습니다.
- 활동 실행 레코드에 `courseSessionId`, `activityInstanceId`, `roomCode`, `matchId`, 상태 등을 연결합니다. 실제 이름은 기존 DB 규칙을 따릅니다. 방 생성은 중복 클릭과 두 교사 탭에도 중복 생성되지 않도록 서버에서 제어합니다.
- 방 생성 완료 후 기존 강의 앱의 실시간 구독으로 학생에게 현재 활동의 방 정보를 전달합니다. 새로 진입한 학생도 서버에서 현재 방을 조회할 수 있어야 합니다. 교사의 로컬 상태만으로 방을 공유하지 않습니다.
- 현재 최대 선수 수는 **30명**입니다. 초과 시 자동 누락시키지 말고 명확히 알리고 참여 대상 선택이나 분반을 지원합니다. 이번 연결에서 30명 제한을 임의로 늘리지 않습니다.
- 학생 재접속은 안정적인 학생 ID와 올바른 재접속 자격으로 처리합니다. 새로고침마다 UUID를 만들어 중복 참가자를 만들지 않습니다.
- 경기 중 새로 들어온 학생은 현재 규칙대로 관전하고 다음 경기에 참가합니다. 종료 후 같은 방 재경기는 새 `matchId`를 갖는 것을 반영합니다.
- Render 재시작으로 방이 사라지면 기존 방 레코드를 만료 처리하고 교사가 새 방을 만들도록 안내합니다. 강의 앱에 저장한 과거 결과는 보존합니다.

## 시작 권한과 기존 경기 규칙

현재 루미 런은 학생도 시작을 요청할 수 있습니다. 이번 요청의 ‘역할별 참가 화면’을 근거로 경기 규칙을 몰래 바꾸지 마세요. 기본은 이 동작을 유지하고, 강의 앱에 명시적인 ‘교사만 시작’ 정책이 있다면 연동 방에서만 클라이언트와 서버 모두 적용하세요. 어느 동작을 적용했는지 완료 보고에 적습니다.

유지할 규칙:

- 맵: 1 초원(입문), 2 공중정원(쉬움), 3 사막(보통), 4 수정동굴(도전), 5 별빛공장(익스트림).
- `rules.mode`: `race`(도착 순서), `last`(꼴찌 선정).
- `rules.count`: 강사가 지정한 선정 인원, 정수 1~30. 시작 시 실제 연결된 참가 대상 수 이하인지 서버에서 확인합니다.
- `rules.duration`: 30 / 45 / 60 / 90은 **코스 길이**이며 제한 시간이 아닙니다.
- `rules.lives`: 0(무한), 1, 3, 5.
- `rules.text`: 결과 제목. 이 활동에서는 ‘이번 발표자’로 전달할 수 있습니다.
- race: 먼저 도착한 N명. last: N명 탈락 시 종료하거나, 첫 완주자가 나왔을 때 탈락자 우선·현재 뒤쪽 순서로 선정합니다. 부모 앱에서 자체 순위 계산으로 대체하지 않습니다.
- 현재 규칙은 **경계 동점 공동 선정**입니다. N=2라도 동점 때문에 3명 이상이 될 수 있습니다. 화면에 ‘선정 목표 2명 · 공동 선정으로 실제 3명’을 표시하고 기본적으로 모두 발표자로 저장합니다. `selectedIds.slice(0, N)`이나 임의 추첨으로 자르지 마세요.
- 정확히 N명만 필요하다는 새 요구가 있으면 기존 공동 선정 정책과 충돌함을 설명하고 별도 정책을 확정합니다. 이 지시서만으로 동점 규칙을 변경하지 않습니다.
- 교사 강제 종료나 완주 부족으로 선정 인원이 N보다 적거나 0명일 수 있습니다. 빈 결과를 임의 학생으로 채우거나 진행 순위로 재계산하지 않습니다. 교사에게 상황을 표시하고 재경기를 제공합니다.

## iframe 초기화와 메시지

현재 지원하는 프로토콜:

```text
iframe URL: GAME_ORIGIN/embed.html?parentOrigin=<encodeURIComponent(강의 앱 origin)>
게임 → 부모: lumi:available, lumi:ready, lumi:start, lumi:end, lumi:result
부모 → 게임: lumi:mount, lumi:start, lumi:stop, lumi:restart, lumi:destroy
```

`lumi:ready`의 `value`는 방 Snapshot, `lumi:result`의 `value`는 GameResult입니다. 현재 `onReady`는 단순 소켓 연결 완료가 아니라 로비 상태 진입 시 호출됩니다.

- 부모 메시지 리스너를 먼저 등록하고 iframe을 로드합니다. `lumi:available` 수신 후 필요한 인증·활동 정보를 준비해 `lumi:mount`를 보냅니다. 준비 순서가 달라도 초기화가 한 번 성공하도록 처리합니다.
- 부모는 `event.origin === GAME_ORIGIN` 및 `event.source === iframe.contentWindow`를 확인합니다. 송신 targetOrigin에 `'*'`를 사용하지 않습니다. 자식도 정확한 부모 origin과 source를 검증합니다.
- 현재 `lumi:mount`를 다시 보내면 기존 게임이 destroy 후 재생성됩니다. 일반 UI 렌더링, 인원 변화, 타이머 갱신 때 반복 전송하지 않습니다. 명단 갱신이 필요하면 별도 업데이트 메시지를 설계합니다.
- 화면을 떠날 때 게임과 이벤트 구독을 정리합니다. React Strict Mode 같은 중복 마운트에도 방·소켓·결과가 중복 생성되지 않도록 합니다.
- `allow="fullscreen"`, 모바일 가로 안내, 터치 영역, 실제 모바일 화면 높이를 확인합니다. iframe 크기는 기존 앱의 사용 가능한 화면에 맞춥니다.

새 옵션을 구현한 뒤 사용할 mount 예시입니다. `entryRole`, `roomCode`, `autoJoin`, `integrationTicket`는 **추가 구현 대상**입니다.

```ts
const config = {
  title: '게임으로 발표자 선정',
  description: '함께 달리고 이번 발표자를 만나요.',
  entryRole: authenticatedRole === 'teacher' ? 'teacher' : 'student',
  participant: authenticatedRole === 'student'
    ? {id: currentStudent.id, name: currentStudent.nickname}
    : undefined,
  activityId: activityInstance.id,
  storageKey: `${courseSession.id}:${activityInstance.id}:${currentUser.id}:${authenticatedRole}`,
  roomCode: activityInstance.roomCode,
  autoJoin: authenticatedRole === 'student',
  integrationTicket: ticketFromLessonBackend,
  map: 1,
  rules: {mode: 'race', duration: 60, lives: 0, count: presenterCount, text: '이번 발표자'},
  serverUrl: `${GAME_ORIGIN.replace(/^https:/, 'wss:')}/ws`,
  joinBaseUrl: lessonActivityUrl,
};
iframe.contentWindow?.postMessage({type: 'lumi:mount', config}, GAME_ORIGIN);
```

변수명과 타입은 기존 강의 앱에 맞추고, 예시 값은 실제 로그인·수업·활동 데이터로 대체하세요. config의 역할 값은 화면 제어에만 사용하며 서버는 검증한 티켓으로 권한을 판단합니다.

## 발표자 결과를 기존 앱에 저장

현재 결과의 핵심 형식:

```ts
type LumiResultSummary = {
  gameVersion: string;
  moduleVersion: string;
  resultVersion: string;
  matchId: string;
  activityId: string;
  rules: {mode: 'race' | 'last'; duration: 30 | 45 | 60 | 90; lives: 0 | 1 | 3 | 5; count: number; text: string};
  selectedIds: string[];
  players: Array<{id: string; name: string; rank: number | null; status: string}>;
  selectionReason: string;
  tieHandling: string;
  endReason: 'normal' | 'timeout' | 'teacher';
  endedAt: string;
}; // 기존 GameResult의 핵심 필드 설명이며 전체 타입을 대체하지 않음
```

- 결과는 `selectedIds`를 기준으로 학생 ID에 연결합니다. 닉네임이 같은 학생이 있어도 다른 사람으로 유지합니다.
- iframe `lumi:result`는 종료 알림과 즉시 화면 표시의 시작점입니다. **브라우저가 보낸 결과만 신뢰해 DB 발표자를 확정하지 않습니다.**
- 게임 서버가 확정한 결과를 강의 앱 서버에서 검증 가능한 방식으로 전달하도록 추가 구현합니다. 기존 인프라에 맞춰 서명된 서버간 webhook 또는 인증된 결과 조회 중 하나를 구현하고, 활동·방·경기 ID가 실제 연결된 값인지 확인합니다. 공개 `/health`나 클라이언트 계산값으로 검증을 대체하지 않습니다.
- 서버 결과 확인 전에 필요하면 ‘발표자 결과 확인 중’으로 표시합니다. 확인 성공 후 강의 앱 서버에서 DB에 저장하고 강사·학생 화면에 공유합니다. webhook 재시도나 네트워크 실패 시 재처리 경로도 만듭니다.
- 결과 저장은 `(activityInstanceId, matchId)` 같은 고유 키로 멱등 처리합니다. 교사와 여러 학생의 이벤트, `onEnd`와 `onResult`, 새로고침으로 같은 발표자를 여러 번 추가하지 않습니다.
- 저장할 항목은 수업/활동 실행 ID, 경기 ID, 선정 학생 ID, 닉네임 스냅샷, 요청 인원, 실제 선정 인원, 규칙, 선정 사유, 종료 사유, 종료 시각입니다. 기존 발표자 데이터 구조가 있으면 거기에 맞춥니다.
- 강사가 원래 지정한 발표자 목록과 연결할 때 기존 앱의 ‘이번 활동 발표자 교체/추가’ 정책을 확인해 적용합니다. 다른 수업이나 과거 경기 기록을 덮어쓰지 않습니다.
- 게임의 선정 순서는 유지하되 공동 선정자를 서로 다른 확정 순위로 표현하지 않습니다. 발표 순서 편집이 기존 앱에 있다면 그 기능으로 연결합니다.
- 닉네임은 현재 게임에서 18자 제한입니다. 초과 이름은 표시 정책을 명시적으로 안내하고 서버와 화면에서 일관되게 적용합니다. 학생 식별 ID는 잘라서 중복시키지 않습니다.

## 검증과 완료 기준

기존 앱 테스트 도구로 의미 있는 통합·권한 검증을 하고, 강사 1개와 학생 2개 이상의 독립 로그인 브라우저에서 실제 게임을 실행하세요.

1. 강사에는 교사 진입만, 학생에는 학생 진입만 보입니다. 처음으로·새로고침·재접속·결과 화면에서도 유지됩니다.
2. 학생이 클라이언트 role·학생 ID·활동 ID를 바꾸거나 교사 명령을 직접 보내도 다른 학생 사칭·교사 조작·다른 수업 참가가 거절됩니다.
3. 기존 닉네임과 안정적 ID로 코드 재입력 없이 같은 방에 접속하고 각자 자신의 캐릭터를 조작합니다. 이름이 같은 두 학생도 구별됩니다.
4. 대상 인원과 접속 인원이 다르게 표시되고, 존재하지 않는 학생을 가짜 선수로 생성하지 않습니다. 초과 인원과 선정 인원 초과를 설명합니다.
5. N=1, N=2 선정과 경계 동점을 검증합니다. 게임 결과의 selectedIds와 앱 발표자 ID가 일치합니다.
6. 브라우저의 가짜 결과 전송으로 발표자 DB를 바꿀 수 없습니다. 같은 결과를 여러 번 받아도 한 번만 저장되고 학생 화면에도 공유됩니다.
7. 강사 새로고침, 학생 중복 탭·재접속, 경기 중 늦은 참가, 교사 강제 종료, 선정 0명, 재경기, Render 방 소실을 처리합니다.
8. 모바일 가로 조작, iframe 높이, 화면 이동 후 소켓·리스너 정리, 기존 독립 게임의 정상 동작을 확인합니다.
9. 로컬과 실제 배포 검증을 구분합니다. 공개 URL/인증이 없어 확인하지 못한 항목을 성공했다고 보고하지 않습니다.

게임 저장소의 설치·빌드 명령은 `npm ci --include=dev` 및 `npm run build`입니다. 게임 코드·서버를 수정했다면 Render에도 새 커밋을 배포해야 하며 강의 앱만 배포해서 새 연동 API를 쓸 수는 없습니다. 운영 중인 수업을 피해 배포하고 인증 환경변수도 함께 적용하세요.

완료 보고에는 변경 파일, 강사·학생의 사용 순서, 설정할 환경변수, 두 프로젝트 각각의 배포 단계, 검증 결과, 남은 제한을 적어 주세요. 실제 Render 주소나 접근 정보만 부족하면 필요한 사항을 구체적으로 알리고 가능한 로컬 구현은 끝내 주세요.
